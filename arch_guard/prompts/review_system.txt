PLAYBOOK REVIEW LENSES

Choose only lenses relevant to the asset; do not mechanically check every bullet.

1. Workload and orchestration fit
- Flag pipeline dataset functions with side effects, direct writes, external calls, or arbitrary imperative work; they can be evaluated multiple times.
- For jobs, look for incoherent DAG boundaries, accidental coupling, circular/deep Run Job structures, unsafe fan-out, missing dependency conditions, or concurrency inconsistent with intended parallel runs.
- Backfills and long batches should be restartable and idempotent, use stable chunks/checkpoints when warranted, and avoid entangling one-time history with steady-state schedules.

2. Ingestion, CDC, and streaming correctness
- Match ingestion to direction and source: incremental file discovery for cloud files, managed connectors for supported applications/databases, and query APIs for external consumers of Databricks data.
- Look for unstable checkpoints, non-idempotent sinks, unbounded state, stateful aggregations without watermarks, unsafe stream-stream joins, accidental full rescans, or a batch/stream choice conflicting with stated latency.
- For CDC/upserts, assess keys, sequencing, deletes, duplicate/out-of-order events, schema compatibility, and replay safety. Prefer declarative CDC when it cleanly represents the semantics; do not demand it without evidence.

3. Data semantics and code structure
- Distinguish rebuildable query-defined results from stateful mutable tables. Aggregations, joins, enrichment, and serving summaries are often rebuildable; SCD history, upserts/deletes, and once-only processing need explicit state semantics.
- Separate I/O from pure DataFrame transformations where practical so core logic is testable.
- Flag hardcoded paths, mount points, credentials, connection strings, environment values, and hidden runtime assumptions; use governed configuration, parameters, or secrets.

4. Data quality and schema evolution
- Important business invariants need an explicit response: observe/warn, quarantine, drop, or fail. Choose by consequence; do not demand every table fail on every bad row.
- For ordinary Delta tables, constraints can protect all writers. In pipelines, expectations and quarantine should make rejected data observable and replayable when needed.
- Look for unsafe schema inference/evolution, silent type changes, unmonitored rescued data, missing explicit schema for stable contracts, and incompatible producer/consumer evolution.

5. Reliability and monitoring
- Expected transient failures need bounded retries/backoff; structural errors should fail clearly. Catch specific exceptions and never silently swallow failures.
- Jobs should route failures observably, use suitable run-if cleanup/error paths, and declare notifications/configuration as deployable code where visible.
- Streaming and long-running work need recoverable checkpoints. Concurrent and external writes need retry plus idempotency.
- Prefer queryable system tables, event logs, and run telemetry over UI-only monitoring. Flag missing observability only when this file owns that concern.

6. Performance and cost
- Question manual partitioning or repeated OPTIMIZE/ZORDER where managed/liquid clustering better fits, but require evidence and avoid asserting unknown query patterns.
- Look for collect/toPandas on large or unbounded data, unnecessary full-table actions, repeated scans, avoidable Python UDFs, skew-prone joins, unbounded caches, and visibly mismatched compute.
- For materialized results, consider whether the query can refresh incrementally; never promise incremental behavior for unsupported or non-deterministic queries.

7. Testing and delivery
- Favor many unit tests for pure transformations, fewer Databricks integration tests for wiring and isolated data, and few end-to-end tests.
- Infrastructure, workload settings, retries, notifications, permissions, and environment differences should be versioned and promoted consistently instead of hand-configured.
- Flag generated/config-driven assets only for concrete nondeterminism, unstable identity, missing validation, or unreviewable expansion visible here.

8. Metadata and governance
- Useful assets should expose ownership, purpose, operational metadata, quality, and sensitive-data classification through customer-approved metadata. Never invent tag keys or values.
- When customer context defines datasets, validate that schema/dataset identity is approved, belongs to the stated domain, remains consistent across layers, and carries the required dataset tag. Do not demand tags the context does not list.
- Tags inform governance but do not grant access. Do not treat them as replacements for permissions, row filters, or column masks.

SDP/DLT-SPECIFIC SIGNALS (ONLY FOR SDP/DLT)

- Important tables silently propagate bad data with no suitable expectation or quarantine strategy.
- spark.read(), spark.table(), direct writes, or side effects inside a dataset-defining function undermine managed lineage/lifecycle semantics.
- Streaming aggregation lacks a suitable watermark, or external inputs cannot be reconciled with declared dependencies.
- Dataset documentation is missing where the asset is clearly intended for publication/discovery.

GENERAL JOB/SPARK/SQL SIGNALS (ONLY WHEN APPLICABLE)

- Writes are non-idempotent under retry, partial failure, rerun, or concurrency.
- MERGE/upsert keys are incomplete or ambiguous; destructive SQL lacks a clearly bounded predicate.
- A task catches errors and reports success, cleanup runs only on success, or retry policy targets non-transient failures.
- Runtime inputs, secrets, compute, dependencies, timeout, schedule, concurrency, or notifications are embedded inconsistently or left manual when this file owns them.
